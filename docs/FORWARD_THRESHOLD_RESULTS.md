# 第二十一轮实验分析：正常校准阈值为何偏高，以及只用过去数据能否修正

**第二十轮只报 37 个正常误报，主要可追溯到登记阈值由一台主机的短时集中通信决定，而评价期几乎没有同类流量。** 在已经打开的 CIC2018 样本里，按过去无标签分数更新阈值，可以检回一部分 Bot。新采集的两段独立评价均未达到“正常误报不超过 1%，同时多检扫描、保留已检出的指令控制通信”的预设条件。

## 为什么是 37 个误报

1. 用第二十轮归档的两个模型和官方流表重放全部 56,817 条已知校准及评价正常流，逐行分数均与归档一致。历史模型在 10,000 条校准正常流上按升序第 9,901 位取阈值 9.119316，严格超过才告警。共有 95 条超过，另有 15 条恰等于阈值，占第 9,891–9,905 位。
2. 95 条中有 88 条和全部 15 条同分记录来自同一源地址发往 TCP/135 的通信。88 条流分属 88 个通信组，时间集中在 2018-02-28 19:42:18–19:49:59 UTC。每条记录此前 60 秒内，同源同协议完成了 799–2,485 条流，访问 24–109 个目的 IP，目的端口始终只有一个。在同一个已训练模型中保留原始 48 字段和阈值，仅将四项历史置零，88 个告警全部消失。数据将这些流标为正常；已核实的 Nmap 活动来自另一台主机。
3. 评价期该源只剩 3 条正常流，过去 60 秒的流数为 13–27，均未误报。校准期其余主机在原阈值下为 **7/9,865（0.0710%）**，评价期整体为 **37/46,817（0.0790%）**。评价期这 37 条中，另一个源的 UDP/500 流贡献了 29 条。两期正常分数的中位数均约 −16.135，但第 99 百分位由 9.119 降至 −6.667。差异集中在决定报警阈值的高分端。[诊断数据](forward_threshold_20261111/cic-tail.json)

## 旧 CIC2018 评分流上的回顾性验证

每个 UTC 15 分钟起点，用严格早于当次告警的过去一小时全部已见样本分数更新阈值。至少需 1,000 条参考，短缺时退回原固定阈值。更新不需要知道当前或过去样本是否为正常流。CIC2018 此处只能重放原实验抽中的流，并非完整上线流量。[旧窗回放](forward_threshold_20261111/cic-retrospective.json)

| 第二十轮已开评价样本 | 正常误报 / 46,817 | 扫描 / 209 | Bot / 2,974 |
|---|---:|---:|---:|
| 历史模型，固定正常阈值 | 37 | 190 | 0 |
| 历史模型，无标签滚动 | 298（0.6365%） | 192 | 858 |
| 原 48 字段模型，同一无标签规则 | 423（0.9035%） | 201 | 66 |

只改变历史模型的阈值，新增 2 条扫描和 858 条 Bot，原 190 条扫描全部保留。两种模型都采用无标签规则时，加入历史却使扫描新检出 6 条、丢失 15 条，净少 9 条；Bot 新检出 806 条、丢失原先的 14 条，净多 792 条。旧评价期结果参与了本轮方案设计，不能用这份回放代替新时段验证。

## 未开封的两个前向场景

CIC2018 全部 20,115,529 行中，第二十轮最后一条已评分记录之后只有 31.931 秒、100 条正常流，没有新的扫描或 Bot。外部复验选用 IoT-23 的 Zeek 记录。5 月、7 月用于训练，9 月、10 月的两台独立正常设备提供 1,826 条正常校准流，随后按原始顺序重放 2018 年 12 月和 2019 年 2–3 月两次 Mirai 采集。两个 HGB 共享 4,096 条正常、4,040 条扫描和 56 条纯 C&C 训练样本；一个用 8 个 Zeek 原字段，另一个加四项 60 秒历史。C&C 仅指作者明确标注的指令控制通信，与 CIC2018 的原生 Bot 分别报告。[原始来源与逐行覆盖](forward_threshold_20261111/iot23-coverage.json) · [IoT-23 原始数据与标注说明](https://www.stratosphereips.org/datasets-iot23)

主要比较对两个模型采用同一无标签滚动规则。固定阈值仅用较早的正常校准流。第三种规则假设正常流 15 分钟后可得到独立可信确认，每次用前 24 小时已确认的正常流更新；实验数据没有提供真实确认到达日志。下表每格均为原模型 → 加历史。各场景独立判断 1% 分母和预算。[完整逐行复算](forward_threshold_20261111/verified-results.json)

| 场景、阈值 | 正常误报 | 扫描检出 | 纯 C&C 检出 |
|---|---:|---:|---:|
| 34-1 固定 | 22 → 3，上限 19 | 0 → 0 / 122 | 0 → 0 / 6,706 |
| **34-1 无标签滚动** | **22 → 3，上限 19** | **0 → 0 / 122** | **0 → 35 / 6,706** |
| 34-1 延迟正常反馈 | 22 → 4，上限 19 | 0 → 0 / 122 | 0 → 0 / 6,706 |
| 49-1 固定 | 1,836 → 13，上限 36 | 5,404,950 → 819 / 5,404,959 | 0 → 0 / 1,922 |
| **49-1 无标签滚动** | **50 → 497，上限 36** | **112,909 → 17,051 / 5,404,959** | **0 → 0 / 1,922** |
| 49-1 延迟正常反馈 | 648 → 14，上限 36 | 1,773,279 → 822 / 5,404,959 | 0 → 0 / 1,922 |

**34-1** 的历史模型实际误报 0.1560%。122 条扫描出现时，无标签参考池都不足 1,000 条，仍用固定阈值，全部漏检。更新在较晚时段生效后，新检出 35 条 C&C，还有 6,671 条未检出。这个场景能考察新阈值对 C&C 的作用，没有给它改变扫描告警的机会。

**49-1** 的历史模型从固定改为无标签更新，新增 16,232 条扫描，但正常误报从 13 增至 497（13.5607%），超过预算 461 条，C&C 仍全部漏检。同用无标签更新，原模型误报 50 条，也超出预算。两臂逐行比较，加历史新增 16,268 条扫描，丢失 112,126 条，净少 95,858 条。更新在 5,297,559 条记录上实际生效，参考池的攻击占比为 99.923%–99.940%。这样的参考池主要反映攻击分数，无法提供正常分数第 99 百分位的可靠估计。

假设有延迟正常确认时，49-1 的历史模型相对自身固定阈值能在预算内多检 3 条扫描（819 → 822），正常误报 13 → 14，原先及更新后检出的 C&C 均为零。它不能证明可以保住僵尸网络控制通信。两次新采集都没有复现“单靠近期无标签分数即可稳定增加合规扫描检出，同时照顾 C&C”的效果。

## 复算、版本与后续使用

本轮在本机完成。72 项测试通过。两个 HGB 各拟合 200 轮、各分配 6 个 CPU 线程，全量盲评分实测进程树峰值约 9.87 核。独立程序核对了结果包 50 个载荷、两臂校准分数、第 1,809 位阈值、各时间块参考池，以及两个场景的 **32,602,236 个逐行判决**。完整 ZIP 为 7,288,519 字节，SHA-256 为 `9a6abd421aa0a08ca5ee02b0c86f5243fe34e057cf4b52fd3f5898e03eaabfe8`。

数据、输入字段、模型、规则和评价条件在评分前冻结于 `aac2e68`。执行版 `3e03a0b` 修正了官方日志列名别名及 Windows 子进程导入错误，此前两次运行均在评价评分前停止。原始登记文件在三个版本逐字节相同。[GitHub 固定运行指南](https://github.com/zhoumeng-creater/tracelight-ids/blob/forward-threshold-lab-v1.2/docs/FORWARD_THRESHOLD_LAB.md)

本轮结果支持把固定阈值对少数集中正常通信的敏感性写进论文，也给出了无标签滚动阈值在攻击占主导时失效的实测例子。若要回答**原 CIC2018 冻结模型在新流量中能否多检扫描且保住原生 Bot**，仍需一段从未评价过、字段相同、同时有正常、扫描和 Bot 真值的按时到达的流记录。仓库已提供先封存预测、后读独立真值的入口。现有两段外部实验均已完成。
