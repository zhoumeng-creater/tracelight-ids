## 旧版执行中的资源问题

`comprehensive-calibration-v1` 将四个 HGB 逐个完成，再逐个执行 72 条 TabM。每个任务使用四个库线程；C 评分、开发评分和配对报告也采用串行循环。独立进程只用于最后的部署成本测量，没有跨训练任务调度或持续资源日志。四线程是库的线程上限，不代表每时每刻使用四核。

旧辅助目标每一步按固定 1,024 行块扫描完整 F。其 `_block` 从 NumPy 切片创建张量并执行 `.to(device)`；发现评分和活跃块重放都会进入这一过程。相同 F 输入因此反复由 CPU 搬到 GPU。分数返回 CPU 后仍需执行 FP64 顺位与梯度计算，重放还逐位核对分数。重复搬运确实存在，但各环节耗时占比需要本批记录，不能只凭代码认定唯一瓶颈。

新版重用每个工作进程内的固定输入张量，并调度独立任务。驻留输入不能改变 canonical 行序、分块边界、分数定义或随机状态；GPU 分数与 CPU 顺位计算之间的必要交接仍保留。

## 启动时决定并发，不改训练配方

启动时使用生成数组，按 13,252 行的输入形状和既定 TabM 配方，测量 1／2／4 个 GPU 工作进程的吞吐。profile 不读取真实 F、C 或开发材料。选择依据是完成规定计算的吞吐、资源容量与执行有效性，不选择算法、学习率、权重或种子。profile 本身有配置与生成输入绑定；同一绑定下可以复用已完成的并发选择结果。

profile 的模型和训练状态不用于正式实验，也不计入 72 条科学轨迹。正式轨迹仍从各自登记的初始化开始，已有正式轨迹则按恢复协议继续。生成数组不能覆盖真实数据的全部活跃梯度块分布，因此 profile 的吞吐不能冒充本批真实训练速度，正式执行仍保留连续资源记录。

独立任务使用独立进程，各自持有模型、优化器、随机状态、抽样流和恢复文件。CPU HGB 队列与 GPU 训练队列同时执行。模型评分和配对报告仍在冻结后串行执行，本修订优先处理 72 条轨迹的训练吞吐。可用并发数由实际 profile 决定，总吞吐提升至少 10% 才增加并发；GPU 和系统内存保留 20% 余量。24 核记录下最多使用四个 GPU 工作进程与一个 HGB 工作进程，各四线程，并为系统保留四核。四个工作进程不一定优于两个。

所有科学设置保持原登记：

- 六种目标、两个学习率、三种种子，以及 G/R/S 三档辅助权重不变。
- 每条轨迹仍为 31,200 步，四个检查点仍为 3,900／7,800／15,600／31,200。
- BCE batch 256、每类 128，辅助评分块 1,024，模型结构、优化器、数值精度和并列处理不变。
- 全部训练任务终结并冻结模型后才打开 C；全部 C 阈值冻结后才进入开发评价。阶段内部并行不会提前越过这些边界。
- 续跑恢复原轨迹，不通过增大 batch、混合精度或变更种子来提高表面利用率。

## 持续记录资源，单独测部署成本

[`resources.py`](../../scripts/comprehensive_batch/resources.py) 以后台线程每五秒采样一次，每次启动写入新的 `resources-<UTC>-<PID>.csv`。协调进程可通过 `set_phase` 标记 profile、训练或评分阶段。日志记录：

- 时间、阶段、协调进程 PID 和本次采样耗时。
- 系统 CPU 使用率，本协调进程及子进程的 CPU 核占用、进程数和 RSS 总和。
- 系统总内存、可用内存、已用内存和使用率。
- GPU 0 整卡利用率、已用／总显存和功耗，以及 `nvidia-smi` 状态。
- 无法访问进程、设备查询超时或其他采样异常。单次监控失败不终止科学任务；日志文件无法写入时停止该监控并输出错误。

CPU 核占用由相邻采样之间同一 PID 及创建时间的 CPU 时间增量计算；首个样本留空，新建或已经退出的短任务可能漏计。RSS 总和可能重复计算共享页面。GPU 指标含其他程序占用，不能称为本任务独占资源；不支持的功耗字段留空，不填零。

并发任务的实际墙钟包含资源竞争。报告需同时保留批次墙钟、各任务耗时、工作量和并发条件，不能把并发下的任务耗时解释成独占设备性能。

正式 CPU 部署基准仍逐模型隔离执行，沿用四线程、固定输入、预热及三轮原始计时。开始基准前结束资源监控，并等待训练、评分及其他计算队列退出，避免监控查询和并发作业污染延迟、吞吐与内存结果。性能 profile、并发生产执行和独占部署基准各有计时范围，不能互相替代。

执行与回传入口见[实验室说明](../COMPREHENSIVE_BATCH_LAB_20261122.md)。本修订的资源效果以实验室 profile 和回传日志为准。
