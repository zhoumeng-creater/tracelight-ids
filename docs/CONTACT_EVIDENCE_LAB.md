# 第二十二轮实验室指南 · 低误报下的端点接触历史

本批检验两个问题。过去 60 秒内，知道“这个源此前是否接触过当前目的端点、对方是否回过包”，能否在已有活动量和服务端口信息之外多检出扫描？用这个条件追加告警，在新的时段里能否守住 1% 正常误报且保留原有的恶意通信告警？此前 CIC2018 正常校准的一次局部失败促成了设计，Zeek 新场景独立评价方法。[研究依据和近邻](CONTACT_EVIDENCE_RESEARCH.md) · [数据、日期与标签](CONTACT_EVIDENCE_DATA.md) · [第十九至二十一轮现有发现的离线回放](flow_replay/index.html)

本机用六份合成日志在 Windows 上走通全部 59 个阶段，包括 8 次 HGB 拟合、12 次实体 GPU 的合成 MLP 拟合、盲评和逐流计时。合成 HGB/MLP 分别缩为 6 轮和 2 轮；正式预算为 200 轮和 80 轮。完整重启复用 59 个阶段，去掉一份成本回执后只重建对应步骤。实际检测效果等实验室按原预算运行后报告。[合成运行核验](contact-evidence-r22-validation.json)

使用先前已经部署的 route-core 环境。复制下面一段到实验室 PowerShell。独立 checkout 和输出目录可以保留，下次运行同一段会继续已完成的步骤。默认从作者服务器取数据，按块重试并校验解压文件的 SHA-256。

~~~powershell
$labRoot = 'D:\zhoumeng\Graduate'
$repo = Join-Path $labRoot 'tracelight-contact-r22'
$release = 'contact-evidence-lab-v1'
if (-not (Test-Path -LiteralPath $repo)) {
    git clone --single-branch --branch $release https://github.com/zhoumeng-creater/tracelight-ids.git $repo

Set-Location -LiteralPath $repo
$actual = git rev-parse HEAD
$expected = git rev-list -n 1 $release
if ($LASTEXITCODE -or $actual -ne $expected) { throw 'The checkout is not on the registered release' }

.\scripts\RUN_CONTACT_EVIDENCE.ps1
~~~

## 一次运行包含哪些对照

- 共 20 次拟合。其中 4 组普通 HGB 和 4 组按攻击族分配训练权重的 HGB 均固定 200 轮，比较单流 8 字段、原四项源历史、加同服务历史、再加具体目的端点历史四种输入。GPU 小型 MLP 对同四种输入各跑三个预定种子（17、29、43），沿用 128/64 隐层及 80 轮预算。各模型共用相同的 8,192 个训练样本；同种子的四个 MLP 共用原 8 列的初始函数和抽样顺序。HGB 是主比较，三个 MLP 种子的结果各自报告。使用既有方法作为实际对照，不重跑 TabM。
- 每组在训练之后的两台正常设备（1,826 条流）上校准，冻结全部模型与阈值，再对两个新场景盲评分。每组每个场景输出 7 套判决：四种输入的独立 1% 阈值、单流的 0.8% 基础告警、保留基础告警后不限制通信模式的追加，以及保留基础告警后仅对符合历史条件的流追加。相当于每个场景 35 套判决，复用同一批分数。全部流量都进入时间窗口，同毫秒互不可见。评估不做测试阈值搜索。
- 两种追加都以 16 字段模型给候选流评分，使用相同的剩余额度。先保留基础告警，剩余校准误报数为 18 减去基础误报数。门控要求同源同协议、同目的端口的历史中至少有一条已知响应包数为零，且当前目的端点此前没有已观察到的响应包。TCP 的回包也可能是 RST。若正常校准没有合格候选，关闭相应追加；有并列分数时保守使用额度。单流 0.8% 基础告警按构造全部保留，相对完整 1% 单流基线是否漏掉攻击需要逐行验证。
- 训练分配单独比较。原训练抽样有 4,096 条正常、4,040 条扫描、56 条纯 C&C。加权组与普通 HGB 共享全部行号、字段和训练参数，仅在训练阶段使用已有的攻击族标签，把攻击总权重平分给两个家族，正常样本和攻击类总权重保持原值。两组在相同判决策略上的扫描、C&C 及其他攻击逐行得失，检验少数 C&C 在训练中是否因权重太低而容易漏检。这是与知识蒸馏及扩大模型都不同的训练对照，不能补充稀缺的独立 C&C 样本。
- 在已知的校准记录中，门控只覆盖 Honeypot 5-1 的 104 条，4-1 的 452 条均未通过。每组自动报告各个采集的基础告警、实际候选和额外误报。部署时不需要知道未来标签，实际误报由未来正常流决定。
- 两个旧训练集的抽样行号和原 8/12 字段 HGB 正常校准分数有第二十一轮封存参照。程序校验行身份并输出分数差及判定变化，可从数据或模型重放偏差追查。

在规则确定后，另对 CIC2018 已打开的旧窗完成一次零拟合复算。88 条既有 TCP/135 校准误报中，85 条此前从同一端点收到过返回包，3 条此前没有联系该端点。88 条均不符合追加规则，其中 40 条单凭端口历史本可通过，是具体端点信息排除了它们。这只验证旧窗的追加资格；保留的基础告警仍可能触发。原始 1 万条校准正常流的 TCP/135 全部来自这台主机。[旧窗复算与来源](contact-evidence-r20/result.json)

## 怎样判断是否有进展

**主要检验在 52-1。** 同一 HGB 的有条件追加同时对照普通 1% 单流模型、无门控的同预算追加。逐个确认双方正常误报均不超过 1%、扫描净增、原先检出的纯 C&C 全部保留、其他已检出攻击没有丢失。原对照一条 C&C 都没检出时，保留能力无从评价。按作者公开计数该段仅 6 条纯 C&C，需列出每条得失。一个场景的通过仅支持该场景。

**60-1 检查新的正常端和其他恶意流量。** 正常误报单独按 1% 检查；与 1% 单流模型相比，分别报告 C&C-HeartBeat 和 DDoS 的新增和丢失。该场景没有纯扫描或纯 C&C。两个场景分母分别计算。IoT-23 的纯 C&C、心跳和 CIC2018 的原生 Bot 使用不同标签，不能用此次结果补写原 Bot 的结论。

**判断历史信息来源。** 同一学习器、同一正常校准规则下比较 16 对 14 列，检验具体端点联系在服务端口统计之外有无作用；比较 16 对 12 列，检验新增联系信息的总作用。有门控和无门控的追加对照检验挑选新增告警是否有作用。每种方法按每个原始标签输出原先检出、当前检出、新增、丢失。HGB 的新时段结果和实际成本共同决定是否值得保留，三个 MLP 种子用于观察结论是否依赖学习器。

## 算力、成本与回传

开头实际运行一次 CUDA 网络前向并记录卡名、设备与显存。独立采集可并行准备；早期数据准备好即可训练，后续两份流日志同步准备。八个 CPU HGB 作业分批并行，共用 CPU 预算，三个种子的 MLP 依次占用一张 GPU。全量盲评分分 CPU 与 GPU 两条队列；MLP 在训练输入上测不同批量的速度及数值一致性。资源日志记录 GPU 利用率、显存、进程树 CPU 与内存。最终 HGB 部署计时独占，按物理到达顺序重算历史，在三个固定片段对照封存的逐行告警；计时含已解码流记录到模型判定，不含原包采集和日志解析。

只回传 `local/contact-r22/contact-results-*.zip` 中最后一次运行产生的 ZIP 和同名 `.sha256.json`。完成状态在包内 `last_invocation.json`，主比较在 `evidence/outcome.json`，各族新增/丢失及原始标签在 `evidence/outcomes/`，成本在 `evidence/cost/`。回传包括冻结模型、校准证据、每流压缩判决及固定抽样分数，原日志、SQLite 和准备表留在实验室。失败包保留堆栈；修复环境后用相同参数再运行，程序校验并复用阶段输出。只检查合成案例可运行 `.\scripts\RUN_CONTACT_EVIDENCE.ps1 -CheckOnly`。
