# 回包计数为零时，原始抓包里有什么

第二十二轮把回包计数为零的流纳入“未回应”历史。60-1 的两个时间片给出了直接反例。62 条官方正常流都能在原始 PCAP 中找到来自日志响应端的首包，日志却把双方包数都记为零。52-1 也有另一种零计数。12,288 条扫描的发起端 SYN 在抓包中清晰可见，随后完整一秒内都没有看到同一连接的反向 TCP 包。[三段抓包及旧判决的逐组核对](packet-audit.json)

## 60-1 的方向与计数

从作者公开的 PCAP 读取两个不重叠的 4 MiB 片段。第一段覆盖已知异常组的首条正常流，第二段覆盖按时间排序的 1,450 条新增误报的中位记录。对每条 TCP 日志，同时查两个方向，以 IPv4 地址、端口和首包的完整微秒时间匹配。用同一日志的物理行号读取第二十二轮标准 HGB 的封存告警。下表保留作者标签。[60-1 作者目录](https://mcfp.felk.cvut.cz/publicDatasets/IoT-23-Dataset/IndividualScenarios/CTU-IoT-Malware-Capture-60-1/) · [复核数据](packet-audit.json)

| PCAP 片段 | 日志组 | 匹配首包 | 抓包方向相对于日志 | TCP 校验复算不通过 | 原始模型告警 → 端点门控告警 |
| --- | --- | ---: | --- | ---: | ---: |
| 首条异常正常流附近，9.79 秒 | Benign，`^c` | 20/20 | 响应端 → 发起端 | 20 | 4 → 4 |
| 同一片段 | DDoS，`C` | 55,168/55,168 | 发起端 → 响应端 | 55,168 | 0 → 55,168 |
| 新增误报中位时刻附近，4.50 秒 | Benign，`^c` | 42/42 | 响应端 → 发起端 | 42 | 4 → 39 |
| 同一片段 | DDoS，`C` | 55,144/55,144 | 发起端 → 响应端 | 55,144 | 0 → 55,144 |

四组首包的实际 IP 方向都是 `192.168.1.195 → 162.248.88.215`，TCP 的八个常规标志位全部置位，双方日志包计数均为零。62 条正常流中有 35 条属于第二十二轮新增误报。日志记作“响应端”的主机已经发出包，有无对应的请求、远端是否收包和回应，仍需通信两端的证据。两个片段按已知故障定位，不能用表中比例估算全采集或新场景的误差率。[首包时间、字节偏移与五元组示例](packet-audit.json)

Bro 2.6.1 源码用 `^` 标记启发式翻转，字母大小写区分日志的发起端和响应端，`C/c` 表示对应方向的校验和异常。TCP 分析器在启用校验时记录异常并提前返回。作者说明这些日志由原 PCAP 生成，公开目录未给出两次生成日志所用的确切二进制版本和选项。本次直接确认了存档字节的校验结果与计数缺口。若在本机网卡完成校验和卸载之前抓包，存档里的校验和也可能不正确，现有证据无法认定远端收到了坏包或认定产生坏校验值的原因。[历史字段定义](https://github.com/zeek/zeek/blob/v2.6.1/scripts/base/protocols/conn/main.bro#L69-L109) · [TCP 校验处理](https://github.com/zeek/zeek/blob/v2.6.1/src/analyzer/protocol/tcp/TCP.cc#L1151-L1169) · [作者数据说明](https://www.stratosphereips.org/datasets-iot23) · [Wireshark 校验和卸载说明](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvChecksums.html)

## 52-1 的对照

52-1 取捕获文件开头 4 MiB，共 83.80 秒。29,813 个完整帧中有 29,801 个可完整解析的 IPv4/TCP 包，其余 12 个均为 ARP、UDP 或 ICMP。表中 12,658 条日志全部匹配到同微秒、同方向的有效校验 TCP SYN 首包。只在片段覆盖完整下一秒时判断该时间窗是否出现反向包。表中第二列使用完整连接日志，第三列使用抓包的首秒，二者计时不同。[52-1 作者目录](https://mcfp.felk.cvut.cz/publicDatasets/IoT-23-Dataset/IndividualScenarios/CTU-IoT-Malware-Capture-52-1/) · [抓包计数](packet-audit.json)

| 作者标签与条件 | 完整日志中的回应证据 | 首包后完整一秒内没有反向 TCP 包 | 第二十二轮标准 HGB 端点门控检出 |
| --- | --- | ---: | ---: |
| 扫描，状态 `S0`、历史 `S` | 12,640 条发包、未见回应 | 12,288/12,288，另有 352 条抵达片段末尾 | 12,640/12,640 |
| 纯 C&C | 4 条发包未见回应，2 条计到回应 | 5/6 | 0/6 |
| C&C-FileDownload | 12 条都计到回应 | 3/12 | 0/12 |

这个片段包含 52-1 的全部 6 条纯控制和全部 12 条控制兼下载通信。与扫描同样呈现“发包未见回应”的 4 条控制流，应算入控制漏检。即使最终计到回应，首秒也可能沉默；12 条下载中有 3 条如此。更新观察时间或用硬门控排除有回应的流，会改变能识别的通信种类。[原始计数及第二十二轮告警](packet-audit.json)

## 告警时可用的输入

在流日志送达时计算以下特征。只依赖本行的协议、双方包数和 IP 字节数、状态、历史和已知丢失字节数。原始包、标签、UID、IP 地址对、采集编号和事后的 1 秒窗口只用于本次诊断。IoT-23 没有逐行写出日志的墙钟时间，实验按文件中的物理到达顺序重放。将完整日志特征用于真实首包告警会提前使用信息。[三态与方向性特征实现](../../src/ids/response_evidence/observations.py) · [Zeek 的日志写出事件](https://docs.zeek.org/en/current/scripts/base/protocols/conn/main.zeek.html)

| 值 | 告警时能够判断的内容 |
| --- | --- |
| 1，已计到回应端包 | 响应端包计数大于零。即使有其他缺口，这些包仍已入账。 |
| 0，已计到发包、未见回应 | 发起端包数和 IP 字节数均为正，响应端两项均为零，状态为 `S0`，`missed_bytes=0`。TCP 历史只含 `S`，或 UDP 历史只含 `D`。该结论限于本记录可见的通信。 |
| −1，回应情况待定 | 其余情况，包括双方零计数、必需计数缺失、发起活动证据不足或日志信号冲突。 |
| 两项方向性标记 | 对每一端分别判断“该端包数明确为零，且出现本方向校验事件”。`C` 对应发起端，`c` 对应响应端。一个标记为零仅表示该组合未出现。 |

`missed_bytes=0` 只表示日志没有报告流内容缺口，不能证明传感器完整捕获了所有包。三态单独比较，另保留两项方向性标记，以检验它们在其他场景的适用性。即使控制流和扫描都被分到 0，这一观测本身也不决定是否告警。

## 重做抓包核验

在已安装本项目的环境中，从仓库根目录执行以下命令。两个完整日志解压后的 SHA-256、实际 HTTP 字节区间、三个 4 MiB 片段的 SHA-256 均会验证。脚本只解析完整、未分片、包含 TCP 全段的 Ethernet/IPv4 帧，并分别计入所有完整帧与可解析 TCP 帧。三个片段的帧时间均按序。抓包片段驻留内存；输出仅含计数和少量复核样例。

```powershell
$logDir = 'data/raw/iot23-contact-20261112'
$oldPackage = Get-Item '../../实验归档/20261112_第二十二轮端点历史/contact-results-*.zip'
python docs/response-evidence/audit_pcap.py --logs $logDir --r22-package $oldPackage.FullName --out output/packet-audit-replay.json
```

实验室只有旧日志时，可省略 `--r22-package`，仍可复核原始包与两端计数。仓库内的 [packet-audit.json](packet-audit.json) 已包含原包 SHA-256 固定后的标准 HGB 比对结果。
