# 第二十四轮 · 固定 1% 误报预算下的八字段漏检

本轮回答两个问题。同一套八字段输入中，响应方向传输量能否补回下载，同时避开普通大流量传输？如需加入最近 60 秒与同一端点的通信历史，能否在另一台受感染设备上补回控制或下载，同时保住原有告警和每日误报预算？

## 为什么要做这次对照

以封存八字段普通 HGB 和早期正常流登记的阈值为基线。在每个采集日或作者试验单元，先以可信正常流数的 1% 向下取整得到允许误报条数，再逐行核对攻击原检、漏检、新增和丢失。不同采集的同一天分别算。

- IoT-23 的 R52 和 H48 在达标日检出了全部 23,165,683 条扫描。R52、H42、H44、H48 的达标日仍漏了 40 条下载、19 条纯控制。40 条下载均为目的端口 80 的 TCP 通信，有双向包计数和较大的响应方向传输。冻结 HGB 在所有树中均未以响应包数、响应 IP 字节或发起包数作分裂。将“响应至少 65,536 IP 字节的 TCP 目的 80”追加到原告警，补回 38/40，四场新增误报 0。R52、H44、H48 的正常流中同服务样本为零；H42 只有 41 条。另一个已打开的采集日里，65 条可信正常同服务流中 12 条超过该阈值，9 条原先未告警。该条件有辨认传输量的作用，其恶意识别能力需要同服务对照。[IoT-23 逐日复核及复算代码](raw-workpoint/RH_RAW_WORKPOINT.md) · [各场的同服务分母](raw-workpoint/web64k_逐日.csv)
- 将早期正常预算中未被 raw 占用的额度分给历史模型，用同一个阈值追加。H44 在原有 2/211 误报上补回 9 条纯控制和 7 条下载。H48 补回 6 条下载，误报保持 20/3,734，两个采集日都达标。H42 只补回 3 条下载，却新增 1,954 条误报。保留 raw 且使用一个历史分数阈值，即使用当日正常标签事后挑阈值，在 H42 的 44 条误报预算内也补不回任何下载。由此可以区分阈值迁移失败和现有分数排序能力不足。[历史分数上界](raw-workpoint/RH_raw8_bounds.csv)
- R21 的 34-1 在 2018-12-22 误报 4/771，漏掉唯一的扫描和全部 3,288 条纯控制。R23 的冻结 raw 在这整个采集的 23,145 行完全复现 R21 分数。扫描流在 0.939 秒内发出 719 个 UDP 包，目的端口 256，近 60 秒同源同协议没有前序流。控制均发往同一端点的 TCP/6667，当日正常中没有这个服务。R23 的追加联系历史补回 2,445 条控制，误报却升至 49，预算只有 7。事后用当日正常标签求上界，保留原告警后，同一历史分数至多补回 284 条控制，扫描仍漏掉。这说明有跨过阈值的证据，也能量出过高的代价。[封存模型跨轮回放及上界](raw-workpoint/r21-34-frozen-r23.json) · [逐行重放](raw-workpoint/audit_34_frozen.py)
- TQH 的 A、B、D 共 36 个达标单元漏掉 2,699 条外部控制。B 组的 324 条全漏。311 条较长控制流的时长一律改成 3 秒，raw 分数逐条不变；冻结树对时长的最大切分点为 2.999299 秒。加一条 UDP/443 且时长至少 30 秒的规则，在 B 组补回 296 条，误报保持 28/21,472。CESNET 骨干网首日的同服务应用流中，有 4,452/14,746 条也触发该条件。作者没有给 IDS 正常真值，因此这里只计算触发率。正式批次把这条规则作为时长条件的反例对照。[48 单元、树分裂与独立 QUIC 对照](raw-workpoint/TQH_AND_CESNET.md)
- IoT-SFC 仅 4 月 10 日有扫描标签，该日原模型误报 3,764/38,189，预算 381；4 月 14–17 日达标，但没有扫描、控制或下载真值。6 天共有 13 条正常 TCP 目的 80 流满足大响应条件，均为新增误报。把不同日期或不同标签体系的分子分母合并，会掩盖这些差别。[SFC 的逐日计数](raw-workpoint/SFC.md)

## 已登记的新采集和判断条件

43-1 是已发布但此前未评分的 IoT-23 设备采集。选取依据是作者公布的原生标签支持，涵盖 20,574,934 条正常、37,911,674 条扫描、3,498 条纯 C&C、14 条 C&C-FileDownload 和 1 条 FileDownload，全文件共 67,321,809 条流（其余为 DDoS、Okiru）。43-1 晚于训练和正常校准，与已打开的 42-1 在同日重叠，在 44-1 开始前约 38 分钟结束。三者来自同一实验室、同一网关的三台受感染设备。逐行比较原始微秒时间加五元组，43-1 与另两份日志的匹配数均为 0。43-1 只覆盖一个 UTC 日，整场与逐日是同一组样本。这一轮检验同一环境向另一台设备的迁移。记录首次送达时可以读取完整时长、计数和字节数。最近 60 秒历史只使用严格早于该记录的日志。[作者场景和标签](https://www.stratosphereips.org/datasets-iot23) · [锁定的数据源](../configs/raw-workpoint-20261113/source.json)

| 比较 | 实验回答的问题 |
| --- | --- |
| 冻结普通 HGB 的 raw 和保留 raw 的联系历史追加（主比较） | 早期正常预算能否迁移，能补回哪些纯控制和下载；已经检出的扫描是否保留 |
| raw 加 TCP 目的 80 且响应 IP 字节至少 65,536；另报只看 TCP 目的 80 的比较 | 单条连接的传输量比端口单独提供多少区分能力；同服务正常流有多少被一起抬高 |
| 单用 contact、单用 quality、保留 raw 的 quality 追加 | 分开计历史模型替换所造成的丢失，以及使用回包计数质量后的新增与误报 |
| raw 加 30 秒 UDP/443 | 长时长条件在不同环境的触发量；如果没有同类 QUIC 控制，记作缺少该项正例 |
| 家族加权 HGB 和 3 个已冻结 MLP | 同一组输入和规则换学习器后是否仍出现相同现象；报告每组，不挑最好一次 |

所有权重、1,826 条早期正常记录的登记分数和不含 IP 的验证特征已随仓库提供。两个历史追加分别使用原模型报过之后的剩余额度，采用严格大于的单一阈值。主 HGB 原阈值占用 7/18 个名额；两个历史追加在早期正常集上分别占用 17/18、15/18。实验室先在当前设备上逐来源重放这些早期正常记录。HGB 连续分数和判决须逐条相同。GPU 保留原严格比较，记录浮点分数、边界翻转与各策略的实测校准误报。早期校准超标的组合在结果中标记。已有本机真实 CUDA 重放发现这种差异；实验室将用自己的 GPU 重测。[冻结工件摘要](../configs/raw-workpoint-20261113/controls.json) · [已有设备重放](raw-workpoint/frozen-score-replay.json)

同一采集整段和每个 UTC 日均报。基线和候选都达标、目标有样本、逐行增检超过丢失，才把该目标记作预算内净收益。若基线全检，报可补漏数 0；若基线已超预算，只追加告警无法使它达标。是否三个目标都有严格增益单列。所有超标日和源标签都保留。每个目标均给出同服务正常分母，事后排序上界只能解释失效。若新增告警主要来自该场景独有端口，或一次换场就超预算，此轮结果不足以选它作主方法。

## 实验室运行

在实验室仓库中执行。运行沿用第二十三轮的 route-core Python 和 CUDA 环境，不需要旧回传包。

```powershell
git fetch origin tag raw-working-point-lab-v1
git worktree add --detach ..\tracelight-workpoint-r24 raw-working-point-lab-v1
Set-Location ..\tracelight-workpoint-r24
.\scripts\RUN_RAW_WORKPOINT.ps1
```

入口会按登记的公开 URL 分块下载原始日志，断点续传并校验**解压后的完整日志**。使用离线副本时，把 `CTU-IoT-Malware-Capture-43-1.conn.log.labeled.gz` 放在同一目录，运行 `.\scripts\RUN_RAW_WORKPOINT.ps1 -SourceDir 'D:\已有数据目录'`。可用 `-Python` 传入解释器绝对路径，`-Threads` 限定 CPU 配额，`-OutputRoot` 指定有空间的本地盘。默认线程取物理核心数，范围 4–64。检查命令为 `.\scripts\RUN_RAW_WORKPOINT.ps1 -CheckOnly`。

在真实日志前 1,447,538 行上，原串行解析用时 37.13 秒，新版 8 进程用时 12.81 秒，输出逐列相同。整个解析阶段实测平均占用 2.19 个 CPU 核，工作进程数和实际核占用分别记录。[数据身份、时段与解析对照](raw-workpoint/SOURCE.md)

下载和解析使用多个工作线程或进程，60 秒历史按带预读窗口的时间块并行构建。两组 HGB 分别调用多核 CPU，三个 MLP 在同一 CUDA 队列依次前向，同时运行 HGB。数据解压和保序合并有串行段。程序记录每阶段时间、进程树 CPU 核数、内存、GPU 利用率和显存。逐条设备探针与资源曲线分别报告。单条成本对照独占 CPU，区分已形成特征的模型成本与全量历史构建成本。此次只重放冻结权重，不做新的模型训练。

完成后回传 `local\raw-workpoint-r24\workpoint-results-*.zip` 及旁边的 SHA-256 文件。包中有每组逐日增失、全场结果、同服务对照、事后排序上界、按标签和决策抽取的有界样本及资源记录。大日志、完整特征和逐行连续分数留在实验室本地，以便必要时核对行号。中断后在原工作树和输出目录再次执行同一命令，复用校验通过的已完成阶段。若生成 `workpoint-incomplete-*.zip`，其中的失败阶段和异常可用于排查。
