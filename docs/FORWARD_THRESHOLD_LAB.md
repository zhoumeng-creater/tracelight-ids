# 第二十一轮：用告警前数据确定低误报阈值

## 第二十轮留下的问题

CIC2018 校准集 10,000 条原标正常流中，23.225.163.149 发往 TCP/135 的一段通信贡献了 95 个误报中的 88 个。15 条同分记录占升序第 9,891–9,905 位，登记使用的第 9,901 位也在其中。后期该主机只出现 3 条正常流。保持阈值不动，其余校准主机的误报为 7/9,865，与前向评价的 37/46,817 接近。固定 48 个原字段及模型，只把这 88 条的四个历史值置零，全部告警消失。该对照解释此次分数上尾的来源，没有改变其标签。

在原 50,000 条前向样本上做过一次回顾性回放。每 15 分钟只取过去一小时内已见样本的分数更新阈值，历史模型误报 298、检出 192 条扫描和 858 条 Bot；原 48 字段模型使用相同规则时分别为 423、201、66。该批评价已经公开，且只保存了抽样流的分数，不能证明新时段效果。[回放数据](forward_threshold_20261111/cic-retrospective.json) · [校准诊断](forward_threshold_20261111/cic-tail.json)

## 两个新时段

CIC2018 在第二十轮最后一条已评分流后只延续 31.931 秒，有 100 条原标正常流，零扫描、零 Bot。外部确认改用 IoT-23 作者原始 Zeek 日志。训练用 2018 年 5 月与 7 月的两个感染场景。先固定分层采样种子，按二元标签各取 4,096 条；以相同 200 轮 HGB 比较八项 Zeek 特征（协议、端口、持续时间、双向包数和 IP 字节数）与另加四项先前 60 秒观测的版本。9 月和 10 月两台独立正常设备的 1,826 条日志仅用于登记正常阈值。R20 的两个模型仍用于同口径 NF-v3，不能直接接收 Zeek 八字段。[UQ 四套同口径数据](https://staff.itee.uq.edu.au/marius/NIDS_datasets/) · [IoT-23 作者、场景、许可与标签定义](https://www.stratosphereips.org/datasets-iot23)

## 预先固定的阈值与比较

两组评分模型各运行三种规则，使用相同记录，跨场景重置历史。各自按升序第 $\lceil 0.99(n+1)\rceil$ 个分数登记，严格超过才告警；并列值不拆开。每条记录仅可利用此前已记录的信息。

| 规则 | 参考分数和可用时间 |
|---|---|
| 固定正常阈值 | 只取先前两台独立正常设备的全量分数，整个评价场景沿用。 |
| **主要比较：无标签滚动阈值** | 每个 UTC 15 分钟边界取过去一小时全体已见流，至少 1,000 条才更新，否则使用固定阈值。不会读取评价真值，攻击可以进入参考池。 |
| 延迟正常反馈，条件对照 | 假设每条正常流在完成 15 分钟后能获独立可信确认，最近 24 小时的参考窗整体后移 15 分钟，且只纳入确认时间严格早于更新时刻的记录。至少 1,000 条才更新。作者未记录真实反馈到达时间。 |

选 1,000 条是为了让 1% 上尾约有十条参考记录，未根据评价分数选参。正常反馈一小时参考池在两个场景最多只有 293、568 条，故在打分前将条件对照固定为 24 小时。仅按时序和标签核查，34-1 的 122 条扫描都在无标签阈值回退期间；49-1 有 5,292,091 条扫描发生在更新生效时。[各窗口覆盖](forward_threshold_20261111/window-coverage.json)

固定模型先对两套完整评价日志盲评分，只读列出的输入字段。历史及阈值按原始日志物理顺序，逻辑时钟取截至该行已见的最大完成毫秒。同毫秒不互用，缺持续时间时使用记录起时。真实采集器发布延迟未随日志记录。判决输出中可区分有反馈假设的条件对照和可直接执行的两个规则。逐场景报告实测误报及预算、扫描和 C&C 分别新增/丢失的数量，并输出更新记录、回退覆盖与参考池攻击比例。同规则比较两种模型，另对每种模型比较更新与固定阈值。

主要比较为两种模型都使用无标签更新。分别检查每个场景的两组是否都不超过 1%、扫描净增、原先至少检出一条 C&C 且全部保留。另列历史模型自身调整阈值是否多检、是否落在预算内。任何一段超预算，都单独报告。两段结果不能用合并样本量替代。

## Windows 实验室运行

使用已装好的 route-core Python。下载时可选作者服务器或已核验的六个离线 gzip。下面的 SourceDir 示例应指向六个文件所在的目录。若使用作者服务器，省略 SourceDir 参数。源数据按解压后的字节校验，可直接使用本机项目的 data/raw/iot23-forward-20261111 目录。

~~~powershell
Set-Location -LiteralPath 'D:\zhoumeng\Graduate'
git clone --branch forward-threshold-lab-v1.2 --single-branch https://github.com/zhoumeng-creater/tracelight-ids.git tracelight-forward-threshold
if ($LASTEXITCODE -ne 0) { throw 'Clone failed' }
Set-Location -LiteralPath 'D:\zhoumeng\Graduate\tracelight-forward-threshold'
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\RUN_FORWARD_THRESHOLDS.ps1 -SourceDir 'D:\zhoumeng\Graduate\iot23-forward-20261111'
~~~

全批只拟合两组 HGB。默认最多使用 24 个物理核，两组拟合和全量批评分分配给两个 CPU 进程，24 核机器上各 12 线程。源文件默认两份并行准备。该 scikit-learn 学习器使用 CPU。资源采样随结果返回；内存紧张可在第一次运行时选择 -PrepareWorkers 1。中断后以相同参数重跑，会核对已完成阶段的摘要并续跑。只做合成检查用 -CheckOnly。

回传 local/forward-threshold-r21 中本次的 forward-threshold-results-*.zip 和对应的 .zip.sha256.json。evidence/paired-outcome.json 为逐场景汇总，evidence 下各场景保留分数、逐行告警和阈值，models/frozen 中有两份模型。

## 将来取得同口径新采集

要检验原第二十轮冻结模型及原生 Bot，可使用同一版本的 ids.threshold_validation.frozen_nfv3。输入为另一段完整 NF-v3 原字段流和独立真值，含物理到达时刻且该时刻等于流结束时刻；观察区间须晚于第二十轮、至少留出 60 秒预热。先执行 score 封存预测，再用 evaluate 揭示真值。两个命令的输入要求见各自 --help。新源须独立核对扫描和 Bot 的定义及覆盖。已打开的第二十轮样本可用 ids.threshold_validation.cic_replay 单独复算。

评分前登记的版本为 `forward-threshold-lab-v1`。执行版 `forward-threshold-lab-v1.1` 补充识别 34-1 作者日志中的详细标签列名 `det_label`。第一次运行在读取该表头时停止，尚未拟合模型。两版使用同一份登记文件。

Windows 执行版 `forward-threshold-lab-v1.2` 将进程入口移入可导入的模块，保证 Python spawn 可在新进程中定位数据准备及拟合函数。修正前的运行都在打分前停止。
